여기까지는 생각보다 순조로웠다.

애플리케이션이 발급한 일회용 코드를 브라우저로 전달하고, Keycloak이 백채널에서 그 코드를 확인하는 데까지는 큰 문제가 없었다. 이제 Keycloak 로그인 흐름에 이 과정만 끼워 넣으면 끝이라고 생각했다.

문제는 실제로 연결한 다음이었다.

## 실패하면 원래 로그인으로 넘겼다

Keycloak의 인증 흐름에 일회용 코드를 확인하는 단계를 추가했다.

요청에 코드가 있고 확인까지 성공하면 해당 사용자로 인증한다. 코드가 없거나 확인에 실패하면 로그인 전체를 막지 않고 기존 아이디·비밀번호 화면으로 넘긴다.

이 기능은 원래 로그인을 대체하는 수단이 아니라, 특정 진입 경로에서만 사용하는 지름길에 가까웠기 때문이다. 애플리케이션이나 네트워크에 잠깐 문제가 생겼다고 모든 사용자의 로그인을 막고 싶지는 않았다.

적용 범위도 필요한 클라이언트 하나로 한정했다. 새 인증 단계를 넣은 흐름을 별도로 만들고 그 클라이언트에만 연결했다.

덕분에 기능이 실패해도 사용자는 평소 로그인으로 돌아갈 수 있었다. 그런데 이 동작 때문에 원인을 찾기 어려운 문제가 생겼다.

## 모든 서버가 200인데 로그인만 안 됐다

브라우저는 정상적으로 Keycloak에 도착했다. Keycloak은 애플리케이션의 코드 확인 API를 호출했다. 애플리케이션 로그에는 성공이 찍혔고, 프록시 로그에도 응답 상태는 200으로 남았다.

그런데 사용자는 로그인되지 않고 비밀번호 입력 화면을 보고 있었다.

처음에는 인증 단계가 아예 실행되지 않은 줄 알았다. 흐름 연결을 다시 보고, 요청에 코드가 들어오는지 확인하고, 백채널 호출도 따라가 봤다. 모두 지나가고 있었다.

더 이상했던 점은 일회용 코드도 이미 사용 처리됐다는 것이다. 호출이 실패한 것도 아니고, 코드가 만료된 것도 아니었다. 서버 쪽 기록만 보면 성공이었다.

결국 HTTP 상태가 아니라 실제 응답 내용을 확인했다. 거기에 원인이 있었다.

## 200이었지만 응답 모양이 달랐다

애플리케이션에는 API 응답을 공통 형식으로 감싸는 처리가 있었다. 프론트엔드가 모든 응답을 같은 방식으로 다루기 위해 성공 여부와 실제 데이터를 하나의 구조에 넣는 기능이었다.

그 처리가 백채널 API에도 그대로 적용됐다.

Keycloak은 응답의 최상위에서 사용자 식별 정보를 찾고 있었다. 하지만 실제 응답에서는 그 값이 공통 응답 구조 안쪽에 들어가 있었다. 애플리케이션은 정상 처리했으니 200을 반환했고, Keycloak은 기대한 위치에서 사용자를 찾지 못했다.

그리고 앞에서 정한 규칙대로 조용히 기존 로그인으로 넘어갔다.

그래서 오류가 없었다. 애플리케이션은 성공했고, 프록시는 200을 전달했고, Keycloak도 로그인 전체를 실패시키지 않았다. 각자 맡은 일은 했지만 서로 약속한 응답 모양만 어긋나 있었다.

백채널 API를 공통 응답 처리에서 제외하자 로그인이 정상적으로 이어졌다.

지금 생각하면 응답 크기가 첫 단서였다. 사용자 식별 정보만 내려간다고 보기에는 응답이 예상보다 컸다. 에러 로그만 찾지 않고 실제로 오간 응답을 먼저 봤다면 훨씬 빨리 발견했을 문제였다.

## 테스트도 같은 부분을 놓쳤다

이 문제는 기존 테스트를 모두 통과했다.

테스트에서는 컨트롤러 메서드를 직접 호출했고, 메서드는 기대한 값을 정확히 반환했다. 하지만 실제 HTTP 응답이 만들어질 때는 컨트롤러 밖의 공통 응답 처리가 한 번 더 개입했다.

테스트한 것은 메서드의 반환값이었고, Keycloak이 받는 것은 최종 JSON이었다.

이후에는 백채널 API를 실제 HTTP 요청으로 호출해 최상위 응답 구조까지 확인하도록 테스트를 바꿨다. 수정 사항을 잠시 되돌렸을 때 테스트가 실패하는지도 확인했다. 그래야 같은 문제가 다시 들어왔을 때 잡을 수 있기 때문이다.

## 마치며

이번 문제는 장애가 커서 오래 걸린 게 아니었다. 아무도 실패했다고 말하지 않아서 오래 걸렸다.

실패하면 기존 로그인으로 넘기는 방식은 서비스 전체를 지키는 데 도움이 됐다. 대신 사용자에게 비밀번호 화면이 보인다는 사실만으로는 코드가 없었던 건지, 인증 단계가 빠진 건지, 백채널 계약이 깨진 건지 알 수 없었다.

결국 확인해야 했던 것은 성공 로그의 개수가 아니라 경계에서 실제로 주고받은 값이었다.

인증 흐름을 붙이는 작업도 마찬가지였다. 각 시스템이 따로 정상인지만 보는 것으로는 부족했다. 한쪽이 보낸 응답을 다음 시스템이 같은 의미로 읽고 있는지까지 확인해야 비로소 로그인이 이어졌다.
