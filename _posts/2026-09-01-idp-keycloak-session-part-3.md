앞선 두 글에서는 문제와 전달 방식을 정리했다.

애플리케이션이 직접 로그인시키면 사용자는 로그인했지만 IdP에는 세션이 남지 않는다. 이를 해결하기 위해 브라우저에는 사용자 정보가 아닌 짧은 수명의 일회용 코드만 전달하고, 코드의 의미는 Keycloak과 애플리케이션 사이의 백채널에서 확인하도록 했다.

이제 남은 일은 이 과정을 Keycloak 로그인 흐름에 연결하는 것이다.

그런데 인증 기능은 “정상적으로 동작하는가”만큼 “망가졌을 때 어디까지 영향을 주는가”가 중요하다. 새로 추가한 기능이 실패했다고 기존 로그인까지 막힌다면, 편의를 위한 기능 하나가 전체 인증 장애의 원인이 된다.

이번 글에서는 이 기능의 실패 범위를 줄인 방법과 구현 후 만난 조용한 실패들을 정리한다.

## 인증 흐름에 새로운 선택지를 추가한다

Keycloak은 브라우저 로그인을 여러 인증 단계의 조합으로 처리한다. 기존 세션을 확인하는 단계, 사용자 이름과 비밀번호를 받는 단계, 추가 인증을 요구하는 단계 등이 하나의 흐름을 이룬다.

일회용 코드를 확인하는 단계도 이 흐름에 추가할 수 있다.

- 요청에 일회용 코드가 있다면 애플리케이션에 백채널로 확인한다.
- 유효한 코드라면 연결된 사용자를 Keycloak에 설정하고 인증을 성공시킨다.
- 코드가 없거나 확인에 실패하면 기존 로그인 단계로 넘긴다.

중요한 것은 마지막 동작이다.

코드가 유효하지 않다고 로그인 전체를 실패시키는 것이 아니라, “이번 인증 방식은 사용할 수 없다”고 판단하고 다음 방식으로 넘어가야 한다. 사용자는 평소처럼 비밀번호 화면을 볼 수 있어야 한다.

Keycloak의 개념으로 표현하면 실패보다 **강등**에 가깝다. 새 기능이 할 수 있는 최악의 일은 로그인을 거부하는 것이 아니라 아무것도 하지 않는 것이어야 했다.

이 원칙은 애플리케이션의 소비 API가 잠시 응답하지 않을 때도 동일하게 적용했다. 백채널 호출이 실패하면 일회용 코드 로그인만 포기하고 기존 로그인으로 돌아간다.

편의 기능은 실패할 수 있다. 그러나 편의 기능의 실패가 기본 기능의 실패가 되어서는 안 된다.

## 전역 흐름이 아니라 필요한 클라이언트에만 적용한다

Authentication Flow는 여러 클라이언트가 함께 사용할 수 있다. 공용 흐름에 새 단계를 바로 추가하면 같은 realm을 사용하는 모든 서비스가 영향을 받을 수 있다.

그래서 기본 브라우저 흐름을 복제한 뒤, 복제본에만 일회용 코드 인증 단계를 추가했다. 그리고 그 흐름을 기능이 필요한 특정 클라이언트에만 연결했다.

영향 범위를 줄이는 방식은 두 겹이었다.

1. 실행 중 문제가 생기면 기존 로그인으로 강등한다.
2. 설정 자체의 적용 범위를 특정 클라이언트로 한정한다.

첫 번째는 런타임 실패를 막고, 두 번째는 잘못된 배치나 설정 변경의 범위를 줄인다.

인증처럼 공유 범위가 큰 시스템에서는 기능의 완성도만큼 배치 단위가 중요하다. 전역 설정을 바꾸지 않아도 되는지가 단순한 운영 편의가 아니라 안전 설계의 일부가 된다.

## 모든 서버가 200인데 로그인만 실패했다

구조를 연결한 뒤 가장 오래 붙잡았던 문제는 명확한 오류가 없는 실패였다.

브라우저는 정상적으로 Keycloak까지 이동했다. Keycloak은 애플리케이션의 코드 소비 API를 호출했다. 애플리케이션 로그에도 성공이 찍혔고 프록시 액세스 로그도 200을 기록했다. 그런데 사용자는 비밀번호 화면으로 이동했다.

서버들이 모두 성공했다고 말하는데 결과만 실패한 상태였다.

원인은 애플리케이션의 공통 응답 처리였다.

많은 웹 애플리케이션은 모든 응답을 동일한 형식으로 감싼다. 성공 여부, 실제 데이터, 처리 시각, 요청 식별자 등을 공통 구조에 넣으면 프론트엔드가 응답을 일관되게 처리할 수 있다.

문제는 이 편의 기능이 서버 간 백채널 API에도 적용됐다는 점이다.

Keycloak은 응답의 최상위에서 사용자 식별 정보를 찾도록 되어 있었다. 하지만 실제 응답에서는 그 값이 공통 응답 구조 안쪽으로 이동했다. HTTP 상태는 200이었지만 Keycloak이 기대한 계약은 깨졌다.

더 곤란한 점은 일회용 코드가 이미 정상적으로 소비됐다는 것이다. 사용자는 다시 시도해도 같은 코드를 쓸 수 없었다. 애플리케이션과 프록시는 성공을 기록했고, Keycloak은 사용자를 찾지 못했기 때문에 조용히 기존 로그인으로 강등했다.

예외도 없고 빨간 로그도 없었다.

결국 백채널 API는 공통 응답 처리 대상에서 제외했다. 서버 간 통신에서는 응답 모양 자체가 계약이기 때문이다. 프론트엔드의 편의를 위한 장치가 모든 HTTP 응답에 적용돼도 되는 것은 아니었다.

이 문제를 찾는 데 가장 도움이 된 것은 오류 로그가 아니라 응답 크기였다. 예상했던 단순한 응답보다 바이트 수가 지나치게 컸다. “무엇이 실패했는가”보다 “왜 응답이 예상보다 큰가”가 원인을 찾는 단서가 됐다.

## 설정은 존재하는 것과 적용되는 것이 다르다

두 번째로 만난 문제는 허용 목록 설정이었다.

백채널 소비 API는 아무 곳에서나 호출할 수 없어야 한다. 호출 가능한 대상을 제한하기 위해 주소 허용 목록을 두었고, 설정이 비어 있으면 모든 요청을 거절하도록 만들었다. 설정 누락이 전체 허용으로 이어지지 않도록 한 것이다.

그런데 설정 파일에는 분명 값이 있는데 애플리케이션에서는 빈 목록으로 읽혔다. 목록을 표현하는 방식과 애플리케이션의 설정 바인딩 방식이 맞지 않았기 때문이다.

fail-closed 설계에서는 빈 설정이 모두 거절로 이어진다. 보안상으로는 올바른 기본값이지만, 운영자 입장에서는 “값을 넣었는데도 설정하지 않은 것처럼 동작하는” 조용한 실패가 된다.

이 경험 이후에는 설정값 자체뿐 아니라 애플리케이션이 최종적으로 해석한 결과도 시작 시점에 검증하도록 했다. 민감한 값을 로그에 그대로 출력할 필요는 없지만, 허용 대상이 몇 개인지와 필수 설정이 유효한지는 확인할 수 있어야 한다.

설정 파일에 글자가 존재한다는 사실은 설정이 적용됐다는 증거가 아니다.

## 애플리케이션이 보는 주소는 사용자의 주소가 아닐 수 있다

주소 허용 목록에도 함정이 있었다.

애플리케이션 앞에 리버스 프록시가 있다면 애플리케이션이 직접 보는 요청 주소는 실제 호출자가 아니라 프록시일 수 있다. 이때 프록시의 로컬 주소를 허용하면 프록시를 통해 들어오는 모든 요청이 같은 출발지로 보일 수 있다.

애플리케이션 코드만 보면 허용 목록이 정상적으로 작동하는 것처럼 보인다. 하지만 외부에서 해당 경로에 접근할 수 있다면 실질적인 제한이 되지 못한다.

그래서 1차 방어선은 네트워크와 프록시 계층에 두고, 애플리케이션의 검사는 프록시를 우회한 직접 접근에 대한 추가 방어로 사용했다. 전달 헤더를 신뢰한다면 프록시가 외부에서 들어온 값을 제거하고 직접 다시 설정하는지도 확인해야 한다.

보안 제어는 코드 한 줄이 아니라 실제 요청이 지나가는 전체 경로를 기준으로 검증해야 한다.

## 조용한 강등은 미설치와 구분되지 않는다

실패 시 기존 로그인으로 강등하는 설계는 가용성 측면에서 유리했다. 하지만 관측 가능성에는 새로운 문제가 생겼다.

일회용 코드가 없을 때는 조용히 다음 인증 단계로 넘어가는 것이 정상이다. 문제는 다음 상황들도 겉으로는 똑같이 보인다는 점이다.

- 인증 확장 모듈이 서버에 제대로 배치되지 않았다.
- 클라이언트에 새 인증 흐름이 연결되지 않았다.
- 애플리케이션이 일회용 코드를 인증 요청에 포함하지 않았다.
- 백채널 응답의 모양이 계약과 달라 사용자를 읽지 못했다.

모두 최종적으로는 비밀번호 화면이 나타난다. Keycloak 로그에도 눈에 띄는 오류가 없을 수 있다.

강등 자체는 유지하되 진단 가능한 흔적을 추가했다. 인증 단계에 진입했는지, 코드가 전달됐는지, 백채널 호출이 성공했는지, 사용자까지 확인했는지를 구간별로 구분해 기록했다. 단, 코드 원문이나 사용자 정보처럼 민감한 값은 남기지 않았다.

실패 사유를 확실히 모르는 경우에는 추측을 로그에 적지 않았다. 소비 API가 여러 실패를 같은 응답으로 처리한다면 Keycloak은 코드가 만료됐는지, 이미 사용됐는지 알 수 없다. 이때 “만료된 코드”라고 단정하면 이후 진단을 잘못된 방향으로 이끈다.

모르는 것은 모른다고 기록하는 편이 정확하다.

## 메서드가 아니라 실제 HTTP 계약을 테스트한다

공통 응답 처리 문제는 단위 테스트를 모두 통과했다.

테스트가 컨트롤러 메서드를 직접 호출했기 때문이다. 컨트롤러는 기대한 사용자 정보를 정확히 반환했다. 하지만 실제 HTTP 응답이 만들어지는 과정에는 컨트롤러 밖의 공통 처리와 직렬화 설정이 추가로 개입한다.

테스트가 확인한 것은 “메서드가 무엇을 반환하는가”였고, 실제 계약은 “네트워크로 어떤 JSON이 전달되는가”였다.

이후 백채널 API 테스트에서는 실제 HTTP 계층을 통과시켜 다음 내용을 확인했다.

- 성공 응답의 최상위 구조가 약속한 형태인지
- 공통 응답 봉투가 추가되지 않았는지
- 코드가 정확히 한 번만 소비되는지
- 만료되거나 재사용된 코드가 같은 방식으로 거절되는지
- 백채널 장애가 기존 로그인 흐름을 막지 않는지

회귀 테스트를 추가한 다음에는 수정 사항을 잠시 되돌려 테스트가 정말 실패하는지도 확인했다. 테스트는 성공할 때 통과하는 것보다, 깨졌을 때 제대로 실패하는지가 더 중요하다.

## 짧게 사는 코드도 운영 수명은 더 길다

일회용 코드의 유효 시간은 매우 짧다. 그렇다고 만료 즉시 기록을 삭제하면 로그인 실패를 조사하기 어려워진다.

사용자가 나중에 “로그인이 되지 않았다”고 문의했을 때 코드가 발급됐는지, Keycloak이 소비 요청까지 보냈는지, 실제로 한 번 사용됐는지는 원인을 크게 좁혀주는 정보다.

그래서 유효 시간과 보관 기간을 분리했다.

- 코드는 브라우저 왕복을 마치면 곧바로 사용할 수 없게 한다.
- 발급 및 소비 여부는 제한된 기간 동안 조사 목적으로 보관한다.
- 정리는 로그인 요청과 분리된 별도 작업으로 수행한다.
- 보관 기간은 조사에 필요한 범위와 개인정보 최소화 원칙을 함께 고려한다.

저장된 값이 직접적인 자격 정보가 아니더라도 사용자 식별과 연결될 수 있다면 불필요하게 오래 보관하지 않는 편이 좋다.

## 마치며

IdP를 거치지 않는 로그인에 Keycloak 세션을 붙이는 작업은 단순히 인증 단계를 하나 추가하는 일이 아니었다.

표준 기능을 사용할 수 없는 제약 안에서 Authorization Code가 안전한 이유를 분해했고, 브라우저에는 의미 없는 일회용 값만 전달했다. 새 인증 단계가 실패하더라도 기존 로그인이 계속되도록 강등 경로를 만들었고, 적용 범위도 특정 클라이언트로 제한했다.

구현 후에는 또 다른 문제가 나타났다. 공통 응답 처리, 설정 바인딩, 리버스 프록시, 조용한 강등처럼 각 구성요소만 보면 정상인 것들이 연결 지점에서 계약을 깨뜨렸다.

이 실험에서 가장 크게 얻은 교훈은 두 가지다.

첫째, 표준을 사용할 수 없을 때는 표준의 모양보다 표준이 보장하는 성질을 먼저 이해해야 한다.

둘째, 인증 기능은 성공 경로뿐 아니라 실패했을 때의 영향 범위와 관측 방법까지 함께 설계해야 한다.

로그인은 성공과 실패만으로 나뉘지 않는다. 모든 서버가 정상이라고 말하면서도 사용자를 인증하지 못할 수 있다. 그래서 이 영역에서는 오류 메시지만 찾기보다, 반드시 있어야 할 단계가 실제로 지나갔는지 하나씩 확인하는 편이 더 빠르다.
