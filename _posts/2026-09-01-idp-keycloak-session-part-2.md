앞선 글에서는 IdP를 거치지 않고 애플리케이션이 직접 로그인 상태를 만들었을 때 생기는 공백을 살펴봤다.

사용자는 로그인했지만 Keycloak에는 세션이 없다. 그래서 세션 조회, 강제 로그아웃, SSO, MFA, 감사 로그가 서로 다른 기준으로 움직이게 된다.

해결하고 싶은 것은 단순하다.

> 애플리케이션이 이미 확인한 사용자라는 사실을 Keycloak에 전달하고, 브라우저가 정상적인 인증 흐름을 거쳐 IdP 세션까지 만들게 한다.

하지만 사용자 식별 정보나 재사용 가능한 자격을 브라우저에 그대로 실어 보낼 수는 없다. 이번 글에서는 이 전달값을 어떻게 설계했는지 정리한다.

## 먼저 떠올린 정공법, Token Exchange

OAuth 2.0에는 Token Exchange라는 규격이 있다. 한 시스템에서 확인한 주체를 바탕으로 다른 형태의 토큰을 요청하는 방식이다. “이 사용자를 이미 인증했으니 여기에 맞는 토큰을 발급해 달라”는 요구와 잘 맞는다.

가능하다면 표준 기능을 우선 검토하는 편이 좋다. 직접 만든 인증 프로토콜은 설계뿐 아니라 운영과 폐기까지 계속 책임져야 하기 때문이다.

다만 현실에서는 기능의 존재와 사용 가능 여부가 항상 같지는 않다. 인증 서버 전체에 영향을 주는 기능을 켜야 할 수 있고, 재기동이나 별도의 권한 정책이 필요할 수도 있다. 하나의 클라이언트 요구 때문에 공용 인증 서버의 설정을 바꾸기 어려운 환경도 있다.

Token Exchange는 설정을 잘못했을 때의 영향도 크다. 특정 클라이언트가 임의의 사용자로 토큰을 교환할 수 있게 되면 단순한 기능 오류가 아니라 사용자 가장과 권한 상승 문제가 된다.

이 실험에서는 Token Exchange를 사용할 수 없다고 가정했다. 또한 외부 시스템과 애플리케이션이 공유하는 비밀값을 Keycloak에 복사하지 않기로 했다.

조건을 정리하면 다음과 같다.

- 인증 서버의 전역 설정을 바꾸지 않는다.
- 기존 비밀값을 다른 구성요소로 확산하지 않는다.
- 브라우저에는 사용자 정보나 재사용 가능한 자격을 노출하지 않는다.
- 성공한 경우에는 표준 OIDC 흐름으로 돌아온다.

표준 기능을 쓸 수 없다면 다음 질문은 “직접 무엇을 만들 것인가”가 아니라 “표준은 왜 안전한가”가 되어야 했다.

## Authorization Code는 왜 브라우저를 지나도 괜찮을까

OIDC의 Authorization Code 흐름에서도 값 하나가 브라우저를 거친다. 그런데 그 값은 비밀번호나 사용자 정보가 아니다. 그 자체로는 의미가 없는 짧은 수명의 코드다.

이 구조가 가진 성질을 네 가지로 나눌 수 있다.

1. 브라우저를 지나는 값에 사용자 정보나 권한을 담지 않는다.
2. 값은 아주 짧게 살며 한 번만 사용할 수 있다.
3. 값의 실제 의미는 서버 간 통신에서만 확인한다.
4. 그 서버 간 통신을 호출할 수 있는 대상을 제한한다.

이 네 가지를 만족한다면 URL에 나타난 값이 로그나 브라우저 기록에 남더라도 피해 범위를 크게 줄일 수 있다. 공격자가 값을 보더라도 누구의 것인지 알기 어렵고, 짧은 시간 안에 먼저 사용해야 하며, 이미 소비됐다면 다시 쓸 수도 없다.

Authorization Code 규격을 새로 구현하려는 것은 아니다. 이미 검증된 구조에서 우리 문제에 필요한 안전 성질만 가져오는 것이다.

## 브라우저에는 의미 없는 일회용 코드만 보낸다

전체 흐름은 다음과 같다.

1. 외부 시스템이 기존 방식으로 사용자 식별 정보를 애플리케이션에 전달한다.
2. 애플리케이션이 전달값을 검증하고 사용자를 확인한다.
3. 애플리케이션이 짧은 수명의 일회용 코드를 만든다.
4. 브라우저가 그 코드와 함께 Keycloak의 인증 엔드포인트로 이동한다.
5. Keycloak의 인증 단계가 백채널로 애플리케이션에 코드를 전달한다.
6. 애플리케이션이 코드를 소비하고 연결된 사용자를 응답한다.
7. Keycloak이 해당 사용자의 세션을 만든다.
8. 이후 과정은 일반적인 OIDC 로그인과 동일하게 진행된다.

브라우저가 전달하는 것은 일회용 코드뿐이다. 코드 안에는 사용자 이름이나 이메일, 역할 같은 정보가 없다. 코드의 의미는 Keycloak과 애플리케이션 사이의 백채널에서만 풀린다.

외부 시스템의 비밀값도 애플리케이션 밖으로 나가지 않는다. Keycloak은 그 비밀값이 무엇인지 알 필요가 없고, 외부 시스템의 암호문을 해석할 수도 없다. Keycloak이 신뢰하는 것은 외부 전달값이 아니라 애플리케이션이 발급한 짧은 수명의 코드다.

## 일회용 코드에 필요한 네 가지 성질

일회용 코드라는 이름만 붙인다고 안전해지는 것은 아니다. 어떤 위협을 막으려는지에 따라 코드의 성질을 구체적으로 정해야 한다.

| 결정 | 막으려는 문제 |
|---|---|
| 충분히 예측하기 어려운 난수 | 유효한 코드 추측 |
| 짧은 만료 시간 | 나중에 로그나 기록에서 발견된 코드의 사용 |
| 한 번만 소비 | 뒤로 가기, 중복 요청, 탈취 코드의 재사용 |
| 원문 대신 해시 저장 | 저장소가 노출됐을 때 코드 원문의 재사용 |

만료 시간은 무조건 짧을수록 좋은 것이 아니라 정상적인 리다이렉트 왕복을 완료할 수 있을 만큼은 길어야 한다. 반대로 사용자 편의를 이유로 몇 분씩 늘리면 탈취된 값이 살아 있는 시간도 함께 늘어난다. 실험에서는 브라우저 왕복만 감당할 수 있는 짧은 시간을 사용했다.

한 번만 소비된다는 조건도 중요하다. 코드를 조회한 다음 별도로 사용 처리하면, 거의 동시에 들어온 두 요청이 모두 “아직 사용되지 않았다”고 판단할 수 있다. 소비 여부 확인과 사용 처리는 하나의 원자적인 동작이어야 한다.

이 부분은 특정 데이터베이스나 프레임워크보다 보장하려는 결과가 중요하다.

> 같은 코드에 여러 요청이 동시에 도착하더라도 정확히 하나만 성공해야 한다.

## 실패 사유를 얼마나 알려줄 것인가

코드 소비가 실패하는 이유는 여러 가지다.

- 존재하지 않는 코드일 수 있다.
- 이미 사용된 코드일 수 있다.
- 만료된 코드일 수 있다.
- 코드와 연결된 사용자가 사라졌을 수 있다.

호출자에게 이 사유를 모두 구분해 알려주면 진단은 쉬워진다. 하지만 외부에서는 특정 코드가 실제로 존재하는지, 한 번 사용된 적이 있는지 탐색할 수 있게 된다.

그래서 외부 응답은 의도적으로 단순하게 만들었다. 성공하면 최소한의 사용자 식별 정보만 반환하고, 나머지는 같은 실패로 취급한다. 세부 원인은 권한이 제한된 내부 로그에서만 확인한다.

여기에는 분명한 대가가 있다. Keycloak에서 바라보면 실패가 “왜 실패했는지 알 수 없는 실패”가 된다. 보안을 위해 응답 정보를 줄였기 때문에 관측 가능성은 별도로 보완해야 한다.

이 결정은 다음 글에서 다룰 ‘조용한 실패’와 직접 연결된다.

## 이 방식이 Token Exchange를 대체하는가

아니다. 이 구조는 표준 Token Exchange의 대체 규격이 아니다. 특정 제약 안에서 동일한 목적의 일부를 달성하기 위해 만든 제한적인 연결 방식이다.

표준 기능을 사용할 수 있고 요구사항에 맞는다면 표준을 사용하는 편이 낫다. 직접 만든 일회용 코드에는 발급, 저장, 소비, 만료, 감사, 장애 대응, 폐기 정책이 따라온다. 작은 코드 조각이 아니라 수명주기를 가진 인증 기능이다.

그럼에도 이 실험에서 얻은 중요한 교훈은 있었다.

표준을 사용할 수 없을 때 가장 먼저 해야 할 일은 표준처럼 보이는 API를 만드는 것이 아니다. 그 표준이 어떤 위협을 막고 있는지 분해하고, 필요한 안전 성질을 하나씩 다시 확인하는 것이다.

여기까지는 전달값의 설계다. 아직 더 중요한 문제가 남아 있다.

새 인증 단계를 Keycloak 로그인 흐름 안에 넣었을 때, 이 기능의 장애가 기존 로그인까지 막아버리면 안 된다. 다음 글에서는 영향 범위를 특정 클라이언트로 제한한 방법과, 모든 서버가 정상 응답을 반환하는데도 로그인만 실패했던 원인을 정리한다.
